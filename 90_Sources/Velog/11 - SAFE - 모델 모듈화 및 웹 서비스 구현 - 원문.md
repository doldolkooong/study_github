# [플레이데이터 SK네트웍스 Family AI 캠프 36기] 1st 프로젝트 - 모델 모듈화 및 웹 서비스 구현

**1st 프로젝트 - 모델 모듈화 및 웹 서비스 구현**

> 📖 오늘 정리 내용
> 1. 분석 코드 모듈화
> 2. 시각화 모듈 분리
> 3. 시계열 모델 모듈 분리
> 4. Streamlit 웹 페이지 구성
> 5. 페이지별 시각화 선정 이유
> 6. 예측 모델 선정 과정
> 7. 최종 서비스의 예측 방식
> 8. 프로젝트를 진행하며 아쉬웠던 점
> 9. 회고

이전 단계에서는 전처리와 DB 적재가 완료된 데이터를 대상으로 간단한 분석과 시각화를 수행했다.

바로 웹 페이지를 구현하기보다 먼저 데이터를 직접 분석해보면서,

- 데이터가 정상적으로 적재되었는지
- 원하는 기준으로 집계가 가능한지
- 어떤 그래프가 데이터를 가장 잘 설명하는지
- 미래 예측에 사용할 수 있을 정도의 시계열이 확보되어 있는지

를 확인했다.

이 과정에서 분석 파일마다 비슷한 시각화 코드와 시계열 예측 코드가 반복되기 시작했다.

따라서 최종 웹 구현에 들어가기 전 공통 기능을 **모델 모듈로 분리한 후**, 검증된 분석 결과를 Streamlit 페이지로 옮기는 방향으로 개발을 진행했다.

---

**1. 분석 코드 모듈화**

처음 데이터 분석을 진행할 때에는 각각의 분석 파일 안에서 직접 `Matplotlib` 그래프를 작성했다.

하지만 인구, 자동차, 교통사고 분석을 늘려갈수록 다음 코드가 반복되었다.

```text
groupby
↓
sum
↓
sort_values
↓
plt.figure()
↓
plt.plot() / plt.bar()
↓
title / xlabel / ylabel
↓
plt.show()
```

시계열 분석도 마찬가지였다.

```text
데이터 정렬
↓
학습 / 테스트 데이터 분리
↓
ARIMA 학습
↓
SARIMA 학습
↓
Prophet 학습
↓
성능 평가
↓
최적 모델 선택
↓
미래 예측
```

분석 파일마다 같은 코드를 작성하면 수정할 때 모든 파일을 변경해야 하고 웹 구현에서도 같은 로직이 반복될 가능성이 높았다.

그래서 공통 기능을

```text
models/
├─ visualization.py
└─ time_series.py
```

형태로 분리했다.

---

**2. 시각화 모듈 분리**

먼저 반복적으로 사용하던 시각화 로직을 `visualization.py`에 분리했다.

프로젝트에서 분석용으로 가장 많이 필요했던 그래프는 크게 세 종류였다.

```text
Line Plot
Bar Plot
Heatmap
```

**Line Plot**

Line Plot은 연도나 월처럼 순서가 존재하는 데이터의 변화를 확인하기 위해 사용했다.

공통 함수 내부에서 먼저 데이터를 집계하고 시간 순으로 정렬하도록 구성했다.

```python
def line_plot(df, x, y, title="시계열 추세"):

    data = (
        df.groupby(x, as_index=False)[y]
        .sum()
        .sort_values(x)
    )

    plt.figure(figsize=(10, 5))
    plt.plot(data[x], data[y], marker="o")
```

따라서 자동차 등록대수, 인구, 사고건수처럼 시간에 따른 증감 추세를 볼 때 재사용할 수 있었다.

**Bar Plot**

Bar Plot은 지역, 연령, 차종과 같이 독립적인 항목 간 크기를 비교할 때 사용했다.

```python
data = (
    df.groupby(category, as_index=False)[value]
    .sum()
    .sort_values(value, ascending=False)
)
```

항목별 값을 내림차순으로 정렬하고 필요한 경우 `top_n`을 지정할 수 있도록 만들어 지역별 사고 TOP 20과 같은 분석에도 사용할 수 있게 했다.

**Heatmap**

Heatmap은 하나의 기준만 비교하는 것이 아니라 두 범주의 조합을 한 번에 확인하기 위해 사용했다.

```python
data = df.pivot_table(
    index=row,
    columns=column,
    values=value,
    aggfunc="sum",
    fill_value=0
)
```

예를 들어

```text
연령대 × 시간대
지역 × 월
지역 × 연도
연령 × 면허종류
```

처럼 두 기준이 동시에 존재하는 데이터를 확인할 때 사용했다.

이렇게 `line_plot`, `bar_plot`, `heatmap_plot`을 공통 함수로 분리하면서 각 분석 파일에서는 어떤 데이터를 어떤 기준으로 보여줄 것인지에만 집중할 수 있도록 했다.

> 실제 `visualization.py`에서도 세 함수가 각각 집계 → 그래프 생성 → 분석용 DataFrame 반환까지 담당하도록 구성했다.

**3. 시계열 모델 모듈 분리**

미래 전망 기능 역시 여러 사고 분석에서 반복적으로 사용할 예정이었기 때문에 `time_series.py`로 분리했다.

처음 비교 대상으로 선정한 모델은

```text
ARIMA
SARIMA
Prophet
```

세 가지였다.

**ARIMA**

```python
model = ARIMA(
    train,
    order=(1, 1, 1)
).fit()
```

ARIMA는 과거 값과 오차를 이용해 시계열의 기본적인 추세를 모델링할 수 있고, 비교적 단순한 시계열 모델이기 때문에 기본 모델로 사용했다.

즉,

> 계절성을 고려하지 않았을 때 어느 정도까지 예측할 수 있는가?

를 확인하기 위한 기준 모델의 역할이다.

**SARIMA**

```python
model = SARIMAX(
    train,
    order=(1, 1, 1),
    seasonal_order=(1, 1, 1, 12)
).fit(disp=False)
```

월별 교통사고 데이터는 특정 계절이나 월에 따라 사고 발생량이 달라질 가능성이 있다.

따라서 SARIMA에서는 `12`개월을 하나의 계절 주기로 설정하여 연간 계절성을 반영할 수 있는지 확인했다.

연 단위 데이터에는 계절 주기를 충분히 만들 수 없기 때문에 코드에서도 SARIMA는 월별 데이터에만 적용하도록 했다.

**Prophet**

Prophet은 추세와 계절성을 비교적 쉽게 모델링할 수 있고 날짜 기반 시계열 데이터를 바로 사용할 수 있다는 장점 때문에 비교 대상으로 선정했다.

월별 데이터에서는 연간 계절성을 사용하고,

```python
model = Prophet(
    yearly_seasonality=(frequency == "monthly"),
    weekly_seasonality=False,
    daily_seasonality=False
)
```

> 이번 프로젝트에서는 일별·주별 데이터가 아니기 때문에 불필요한 계절성은 비활성화했다. 세 모델의 구현 방식은 실제 `time_series.py`에 공통 함수로 분리되어 있다.

**4. 어떤 모델이 좋은지 어떻게 판단할까?**

특정 모델을 처음부터 정답으로 정하기보다 동일한 데이터를 각각의 모델로 예측한 뒤 오차를 비교하는 방식을 선택했다.

사용한 평가 지표는

```text
MAE
RMSE
MAPE
```

세 가지이다.

- **MAE**: 실제값과 예측값의 절대적인 차이를 평균낸 값. 전체적으로 예측값이 실제값과 얼마나 차이가 나는지를 직관적으로 확인하기 위해 사용했다.
- **RMSE**: 큰 오차에 더 큰 패널티를 주기 때문에 특정 기간에서 예측이 크게 벗어나는 모델을 확인할 수 있다.
- **MAPE**: 실제값 대비 예측 오차를 비율로 확인할 수 있기 때문에 규모가 다른 시계열의 예측 성능을 비교하기 쉽다는 장점이 있다.

```python
return {
    "MAE": round(mae, 2),
    "RMSE": round(rmse, 2),
    "MAPE": round(mape, 2)
}
```

이번 구현에서는 최종적으로 모델을 `MAPE`가 낮은 순으로 정렬했다.

```python
result_df = (
    pd.DataFrame(results)
    .T
    .reset_index()
    .rename(columns={"index": "model"})
    .sort_values("MAPE")
)
```

즉,

> ARIMA가 항상 좋다 / Prophet이 항상 좋다

라고 정하지 않고 실제 데이터를 이용해 모델별 성능을 비교한 뒤 가장 오차가 작은 모델을 선택하는 구조로 만들었다.

**5. 웹 서비스 구현**

분석 가능성을 확인한 이후 최종 서비스는 Streamlit 기반 멀티페이지 구조로 구현했다.

메인 카테고리는

```text
인구
자동차
교통사고
제도
FAQ
미래 전망
```

으로 구성했다.

각 카테고리 아래에는 상세 분석 페이지를 별도로 두었다.

실제 Streamlit navigation에는 인구 2개 상세 페이지, 자동차 등록·면허·자진반납 관련 페이지, 교통사고 세부 분석 페이지, 정책 페이지 및 미래 전망 페이지가 각각 등록되어 있다.

분석 단계에서는 `Matplotlib`을 이용해 그래프가 적절한지 빠르게 확인했다면 최종 웹에서는 Plotly를 이용해 사용자가 데이터를 직접 확인할 수 있는 인터랙티브한 시각화를 구현했다.

또한 기본 Streamlit 사이드바 대신 상단 메뉴를 만들어 서비스의 카테고리 구조가 한눈에 보이도록 구성했다.

> 메인 페이지 역시 인구·자동차·교통사고·제도·FAQ를 각각 빠르게 이동할 수 있는 카드 형태로 배치했다.

---

**6. 페이지별 그래프를 선택한 이유**

그래프는 단순히 여러 종류를 보여주기 위해 선택한 것이 아니라 각 데이터에서 사용자가 확인해야 하는 질문에 맞게 선택했다.

**👥 인구 페이지**

인구 데이터에서 가장 중요한 질문은

> 고령인구가 얼마나 존재하고, 시간이 지나면서 어떻게 변화하고 있는가?

였다.

따라서 지역별 인구처럼 한 시점의 규모를 비교할 때는 Bar Chart, 연도·월별 변화는 Line Chart가 적합하다고 판단했다.

또한 지역과 연도를 동시에 볼 경우에는 Heatmap 형태를 이용하면 특정 지역의 증가·감소 패턴을 비교하기 쉽다.

인구 페이지를 `지역별 인구 현황`과 `주민등록 인구 현황`으로 나눈 것도 연도 단위의 지역 비교와 월 단위의 세밀한 추세를 구분해서 보기 위해서였다. 실제 navigation도 두 상세 페이지로 구성되어 있다.

**🚗 자동차 페이지**

자동차 페이지에서는 단순 등록대수뿐 아니라

```text
자동차 등록
운전면허
연령
성별
지역
자진반납
```

처럼 여러 기준을 비교해야 했다.

따라서 항목 간 규모 비교가 많은 자동차 데이터에는 Bar Chart를 중심으로 사용했다.

예를 들어

```text
지역별 등록대수
차종별 등록대수
성별 면허 보유
연령별 면허 보유
지역별 자진반납
```

등은 각각의 범주에서 어떤 항목이 큰지 확인하는 것이 핵심이다.

반면 연도별 등록대수나 고령운전자 면허 보유 변화는 시간의 흐름이 중요하기 때문에 Line Chart가 더 적합했다.

그리고

```text
지역 × 연도
연령 × 면허 종류
지역 × 성별
```

처럼 두 기준을 동시에 비교하는 경우는 Heatmap을 사용했다.

이렇게 한 페이지에 모든 정보를 넣는 대신 최종 서비스에서는 `연도별 자동차 등록`, `지역별 자동차 등록`, `성별·연령별·지역별 운전면허`, `자진반납`을 각각 상세 페이지로 분리했다.

**⚠️ 교통사고 페이지**

교통사고 데이터는 이번 프로젝트에서 가장 많은 조건을 가지고 있었다.

```text
연령
지역
연도
월
시간대
사고유형
날씨
```

따라서 하나의 그래프만으로는 데이터를 설명하기 어렵다고 판단했다.

- **Bar Chart**: 연령대별 사고, 지역별 사고, 시간대별 사고, 기상상태별 사고, 사고유형별 사고처럼 규모 자체를 비교할 때 사용했다.
- **Line Chart**: 연도별 사고, 월별 사고, 특정 지역 사고 추세처럼 시간 흐름을 확인해야 할 때 사용했다.
- **Heatmap**: 연령대 × 시간대, 월 × 시간대, 지역 × 월처럼 두 조건의 조합이 중요할 때 사용했다.

예를 들어 단순히 "몇 시에 사고가 많다"가 아니라

> 어떤 연령대가 어떤 시간에 사고가 많은가?

를 확인하려면 일반적인 Bar Chart보다 Heatmap이 더 직관적이라고 판단했다.

실제 분석 검증 단계에서도 연령대·시간대 교통사고를 Heatmap으로 구성했다. 지역·월별 고령운전자 사고 역시 시도와 월을 기준으로 Heatmap을 사용했다.

**📋 제도 페이지**

정책 데이터는 교통사고 데이터와 성격이 달랐다.

숫자를 비교하는 것보다

```text
어떤 정책이 있는가?
대상은 누구인가?
지역마다 지원 내용이 어떻게 다른가?
어떻게 신청하는가?
```

를 확인하는 것이 더 중요했다.

따라서 모든 정책 데이터를 억지로 그래프로 표현하지 않고 정책 정보와 비교 기능 중심으로 페이지를 구성했다.

다만 고령운전자 교통안전교육 데이터는 날짜와 교육정원이라는 명확한 수치 데이터가 있었기 때문에 월별 변화는 Line Chart로 표현할 수 있었다.

최종 서비스에서도

```text
운전면허 자진반납 안내
운전면허 자진반납 정책
정책 비교
자진반납 정책 비교
고령운전자 교육 현황
전국 고령운전자 정책
지역 특화 고령운전자 정책
```

으로 기능을 분리했다.

즉 정책 페이지에서는 그래프를 많이 보여주는 것보다 실제 의사결정에 필요한 정보를 비교하기 쉽게 만드는 것을 우선했다.

**❓ FAQ 페이지**

FAQ는 통계 분석 페이지가 아니기 때문에 그래프를 사용하지 않았다.

사용자의 목적은

> 원하는 질문을 얼마나 빨리 찾는가?

이기 때문이다.

따라서

```text
키워드 검색
+
카테고리 필터
+
질문별 Expander
```

구조를 사용했다.

실제로 FAQ 페이지에서는 `text_input()`을 이용한 검색창과 카테고리 버튼을 제공하도록 구현했다.

즉 데이터라고 해서 무조건 시각화하는 것이 아니라 사용자의 목적에 맞는 UI를 선택하려고 했다.

**7. 미래 전망 페이지**

미래 전망 페이지는 다른 페이지와 조금 다르게 구성했다.

단순히 하나의 지표를 예측하기보다 SAFE에서 중요하게 본

```text
65세 이상 인구
65세 이상 운전면허 소지자
고령운전자 교통사고
```

세 가지 흐름을 함께 보여주도록 했다.

세 지표를 개별적으로 예측 그래프로 보여주면서 현재 실측값에서 미래 값이 얼마나 변화하는지 함께 표시했다.

최종적으로 세 지표를

```text
65세 이상 인구
65세 이상 면허 소지자
고령운전자 사고
```

순으로 나란히 보여주어 고령화가 진행되는 과정에서 면허와 사고가 함께 어떻게 변화하는지 비교할 수 있도록 했다.

또한 결과를 단순 예측값으로 끝내지 않고 지역별 정책 대응 우선순위와 연결했다.

미래 고령인구 변화, 현재 사고율, 예상 사고 규모 등을 이용해 지역별 상대적인 우선순위를 제시하도록 구성했다. 이 지수는 코드에서도 절대적인 위험확률이 아니라 지역 간 상대 비교용 정책 우선순위라고 명확하게 표현하고 있다.

---

**8. 분석 모델과 최종 웹 예측 모델이 달라진 이유**

이 부분이 이번 프로젝트에서 가장 고민했던 부분 중 하나였다.

분석 단계에서는

```text
ARIMA
SARIMA
Prophet
```

을 비교하고 MAE, RMSE, MAPE를 이용해 최적 모델을 자동 선택하는 기능까지 구현했다.

하지만 실제 데이터를 적용하면서 문제가 생겼다.

**시계열 데이터의 기간이 충분히 길지 않았다.**

특히 일부 연도별 데이터는 실측값이 몇 년밖에 없거나, 지역별로 세분화할 경우 사용할 수 있는 연도가 더 줄어들었다.

SARIMA처럼 계절성을 학습해야 하는 모델은 충분한 계절 주기가 필요하고 ARIMA와 Prophet 역시 짧은 데이터에서 장기간을 예측하면 모델이 계산한 값은 나오더라도 그 결과를 신뢰할 근거가 부족했다.

그래서 최종 웹에서는 복잡한 모델의 결과를 무조건 보여주기보다 현재 확인 가능한 추세를 중심으로 Linear Trend와 시나리오 전망을 사용했다.

또 실측 연도가 한 개뿐인 경우 임의로 회귀선을 생성하지 않고 주민등록 인구 장기 변화나 고령인구 변화에 연동한 시나리오를 사용했다.

즉,

> 복잡한 모델을 사용했다는 것보다 현재 데이터에서 어느 정도까지 말할 수 있는지를 구분하는 것이 더 중요하다고 판단했다.

ARIMA·SARIMA·Prophet 비교 기능은 데이터가 충분히 확보되었을 때 확장할 수 있도록 모델 모듈로 남기고, 현재 서비스에서는 해석 가능한 수준의 전망만 제공했다.

**9. 구현하며 아쉬웠던 점**

**1) 가장 큰 한계는 데이터 기간이었다.**

처음에는 시계열 모델을 이용해 장기적인 사고 건수까지 예측하는 것을 목표로 했다.

하지만 2021~2025년 수준의 짧은 연도별 데이터만으로 5년, 10년 뒤를 예측하면 예측 모델을 적용할 수는 있어도 신뢰할 수 있는 예측이라고 보기 어려웠다.

특히 정책 변화, 면허 자진반납 확대, 교통환경 변화, 자율주행 및 운전자 보조기술 발전과 같은 외부 요인이 전혀 반영되지 않는다.

최종 웹에서도 이 문제를 고려해 장기 전망은 확정적인 미래값이 아닌 참고용 지표라고 명시했다.

**2) 데이터마다 연령 기준이 달랐다.**

한 데이터에서는 `65세 이상`으로 제공되지만 다른 데이터에서는

```text
60~69세
70~79세
80~89세
```

와 같은 구간으로 제공되었다.

따라서 정확한 65세 이상 인구를 계산할 수 없는 경우가 있었다.

최종 구현에서는 `60~69세` 인구 중 절반을 `65~69세`로 간주하고 70세 이상 인구를 더하는 방식으로 근사했다.

이 방법은 서비스 프로토타입에서는 비교 기준을 만들 수 있지만 실제 행정 정책 의사결정에 사용하려면 5세 단위 또는 1세 단위 인구 데이터를 확보하는 것이 더 적절하다.

**3) 지역명 표준화 작업이 예상보다 많았다.**

같은 지역도 데이터 출처에 따라

```text
서울
서울특별시
경기
경기도
전북
전북특별자치도
```

등으로 다르게 표현되었다.

최종 미래 전망 페이지에서는 이를 동일한 지역으로 인식시키기 위해 별도의 `REGION_MAP`을 만들어 표준화했다.

처음 데이터 정의 단계에서부터 지역 코드 기반의 공통 Dimension Table을 더 적극적으로 적용했다면 이후 페이지마다 지역명을 정리하는 작업을 줄일 수 있었을 것 같다.

**4) 분석 코드와 웹 코드 사이에 중복이 남았다.**

시각화와 시계열 분석 일부는 `models`로 분리했지만 최종 Streamlit 페이지에서는 UI 구성, 데이터 조회, 전처리, 집계, 시각화가 하나의 파일 안에 함께 존재하는 부분이 많아졌다.

예를 들어 교통사고 페이지에서는 DB 조회뿐 아니라 컬럼 탐색과 연령 범위 처리 같은 보조 함수도 같은 페이지에 들어가 있다.

프로젝트 기간이 더 있었다면

```text
services/
    ├─ people_service.py
    ├─ car_service.py
    ├─ accident_service.py
    └─ policy_service.py

models/
    ├─ visualization.py
    └─ time_series.py

pages/
    └─ UI만 담당
```

처럼 데이터 조회·분석 로직과 화면 코드를 더 명확하게 분리하고 싶다.

**5) Streamlit 페이지 파일이 너무 커졌다.**

Streamlit 기본 UI를 그대로 사용하는 것이 아니라 SAFE 서비스에 맞는 화면을 만들기 위해 CSS와 HTML을 많이 사용했다.

덕분에 기본 Streamlit 대시보드보다는 서비스 형태에 가까운 화면을 만들 수 있었지만 페이지별 코드의 길이가 크게 증가했다.

공통 Navigation, CSS, 카드 UI 등을 컴포넌트로 분리했다면 코드 중복을 더 줄일 수 있었을 것 같다.

**6) 정책 데이터의 정량 분석이 부족했다.**

교통사고, 인구, 자동차 데이터는 수치형 데이터가 충분해 다양한 그래프와 지표를 만들 수 있었다.

하지만 정책 데이터는 정책명, 대상, 지원 내용 등 텍스트 데이터가 많아 현재 서비스에서는 주로 조회와 비교 기능으로 구현했다.

추후에는

```text
정책 시행 전·후 사고 변화
면허 반납 지원금과 반납률 관계
교육 참여율과 사고 감소 관계
지역별 정책 시행 여부와 사고율 비교
```

처럼 정책 효과를 수치적으로 평가할 수 있는 데이터까지 확보한다면 서비스의 정책 활용도를 높일 수 있을 것 같다.
